第一章 · DWS 基础

DWS 是什么？

DingTalk Workspace CLI

DWS 是面向钉钉工作台能力的命令行工具，负责认证、群聊、联系人、机器人和事件流操作。

本项目中的位置

DWS 不执行 AI，它负责把群消息送进 Worker，并提供群、成员、机器人等管理能力。

理解 DWS 的关键：它是消息与钉钉资源的控制入口，不是模型执行引擎。

第二章 · Agent 抽象

业务层只认识一个入口

runAgent(agent, prompt, sessionId, config, callbacks) agent === "pi" → runPi(...) agent === "codex" → runCodex(...) agent === "opencode" → runOpenCode(...)

统一输入

Prompt、Session ID、工作目录、模型和事件回调。

统一输出

AgentResult：sessionId、text、toolStats、durationMs。

思考题

为什么不在 group-worker 里直接 spawn Pi 或 Codex？

答案：隔离协议差异，后续替换 Agent 不需要改消息业务。
第二章 · Pi

Pi：RPC 长连接

spawn pi--mode rpc
→
get_state拿 sessionId
→
promptJSON stdin
→
JSONL 事件delta / tool / settled

实时能力

text_delta 持续更新卡片；tool_execution_start 展示工具调用。

运行中引导

新消息可以转换为 steer 指令，直接写入正在运行的 Pi 进程。

Pi 的核心关键词：RPC、持续进程、增量事件、steer。
第二章 · Codex

Codex：Exec 单轮进程

codex exec --json --skip-git-repo-check \ --dangerously-bypass-approvals-and-sandbox \ --cd <workDir> - stdin → Prompt stdout → thread / tool / message / turn.completed

新会话

使用 codex exec，并通过 --cd 指定工作目录。

恢复会话

使用 codex exec resume <sessionId>，继续原有上下文。

Codex 当前轮结束后进程退出；后续消息由本地队列合并为下一轮任务。
第二章 · OpenCode

OpenCode：单轮 CLI 会话

opencode run --format json \ --dir <workDir> --auto \ --model <agentModel> \ --session <sessionId> "Prompt"

启动与恢复

首次运行不带 session；后续运行通过 --session 恢复上下文。

事件处理

读取 JSONL stdout，识别 text/message、tool/tool_use 和 error 事件，最终统一转换为 AgentResult。

源码实现：opencode-agent.ts 使用 config.opencodeCliPath，工作目录为 codexWorkDir，模型通过 --model 传入。
第二章 · 对比

相同的出口，不同的节奏

维度PiCodexOpenCode
启动方式pi --mode rpccodex exec --jsonopencode run --format json --dir <workDir> --auto
通信方式JSON RPC / JSONLstdin Prompt + JSONL stdoutPrompt 命令行参数 + JSONL stdout

上层看到的是同一个 AgentResult，因此回复层可以统一处理。

第六章 · 机器人 Webhook

Webhook：主动把结果发到群里

业务服务 → HTTP POST（JSON）→ 群自定义机器人 Webhook → 群消息

5 种 msgtype

text、markdown、link、actionCard、feedCard。

和消息接收分开理解

这里讲主动发送，不是 DingTalk Stream 接收消息，也不是互动卡片更新协议。

Webhook 地址含凭证，不能写进 PPT 或公开日志；发送时遵守机器人的关键词、加签或 IP 安全设置，检查响应中的 errcode。
第六章 · 机器人 Webhook

text：纯文本

{ "msgtype": "text", "text": { "content": "Pi-Agent任务完成，导出充值记录3197条" }, "at": { "isAtAll": false, "atUserIds": [ "manager1" ] } }
适合任务完成通知、状态提醒。atUserIds 使用实际用户 ID；示例记录数仅用于演示。
第六章 · 机器人 Webhook

markdown：格式化报告

{ "msgtype": "markdown", "markdown": { "title": "今日充值报表", "text": "#### ✅任务执行完成\n- 记录总数：**3197条**\n- [打开AI表格](https://example.com/report)" }, "at": { "isAtAll": false } }
推荐用于带标题、粗体、图片和链接的报告；不要依赖完整 Markdown 渲染，表格建议改成列表。标题优先用 ####，颜色标签等扩展需在目标客户端验证。
第六章 · 机器人 Webhook

link：单链接卡片

{ "msgtype": "link", "link": { "title": "打开充值表格", "text": "今天全部充值记录已导出", "messageUrl": "https://example.com/report", "picUrl": "https://example.com/report.png" } }
一个标题、摘要和图片对应一个跳转地址。示例 URL 需替换为实际报表地址。
第六章 · 机器人 Webhook

actionCard：按钮卡片

{ "msgtype": "actionCard", "actionCard": { "title": "充值报表已生成", "text": "#### ✅完成\n共3197条充值记录", "hideAvatar": "0", "btnOrientation": "0", "btns": [ { "title": "打开表格", "actionURL": "https://example.com/report" } ] } }
适合报表入口。btns 为独立跳转按钮；整体跳转使用 singleTitle + singleURL，不与 btns 混用。它不是可流式更新的互动卡片。
第六章 · 机器人 Webhook

feedCard：多图文链接列表

{ "msgtype": "feedCard", "feedCard": { "links": [ { "title": "报表A", "messageUrl": "https://example.com/a", "picUrl": "https://example.com/a.png" }, { "title": "报表B", "messageUrl": "https://example.com/b", "picUrl": "https://example.com/b.png" } ] } }
适合一次发送多份报表或资讯，每个条目有自己的标题、图片和跳转地址。

分享练习

请你判断：这条消息会不会触发 Agent？

场景：群 G1 中用户 U1 发送了一条消息；机器人已经在群；但是配置 targets 中只有 G1 + U2。

问题：这条消息会进入 GroupQueue 吗？

不会。acceptsTarget 要求 groupId + senderId 同时匹配，G1 + U1 不命中。

场景：用户执行“打开 AI”，机器人不在群，但 Dashboard 未配置 Client ID。

问题：系统会怎样？

不会自动加群，会发送失败提示，要求先配置 Client ID 或手动加群。
